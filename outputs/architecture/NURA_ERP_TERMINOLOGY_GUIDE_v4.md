# NURA ERP — Terminology Guide

**Статус:** пополняемый проектный справочник  
**База:** Part 00 rewrite + `ENGAGEMENT_MEMORY` v1.4  
**Назначение:** дать единое краткое толкование английских терминов, которые намеренно сохраняются в архитектурных документах NURA ERP.

## 1. Языковой стандарт для архитектурных Parts

Документы NURA ERP рассчитаны одновременно на руководство, бизнес-пользователей и технических специалистов. Поэтому применяется следующий принцип:

- заголовки первого уровня Parts (`00.`, `01.`, `02.` и т. д.) сохраняются на английском; заголовки ниже первого уровня пишутся преимущественно по-русски, сохраняя английские названия принятых сущностей, функций, состояний, ролей и иных устойчивых терминов;
- основной поясняющий текст пишется на грамотном русском языке;
- английские союзы, предлоги, обычные общеупотребительные слова и разовые описательные обороты не используются без необходимости;
- если английский термин важен для разработчиков или принят в рабочей речи NURA, но может быть непонятен нетехническому читателю, при первом употреблении предпочтителен формат: русское пояснение (**English term**);
- в пояснениях этого справочника английские слова используются только как ссылки на термины, которые сами имеют отдельную расшифровку в справочнике, либо как собственные наименования систем, организаций, технологий и форматов;
- один и тот же термин должен использоваться последовательно во всех Parts; перевод не должен создавать второе конкурирующее название одной сущности;
- очень общие слова без специального архитектурного смысла в справочник отдельно не включаются;
- внутри каждого тематического раздела термины располагаются в алфавитном порядке по английскому наименованию.

Справочник пополняется по мере появления новых существенных терминов в Parts 01–08.

## 2. Термины Research Administration и Project

| Термин | Краткое пояснение |
|---|---|
| **Application** | Заявка на финансирование или участие в программе; самостоятельный **Business Object**, не равный **Project**. |
| **Award** | Положительный результат **Funding Decision**: присуждение финансирования или права на реализацию. |
| **Bid** | Конкурсное/коммерческое предложение в сценариях, где работа ближе к контракту или тендеру, чем к грантовой заявке. |
| **Closed** | Закрытое состояние **Project** или **Agreement / Contract** в соответствующем контексте закрытия. |
| **Closure-Blocking Condition / Obligation** | Условие или обязательство, которое должно быть выполнено до закрытия конкретного родительского объекта. |
| **Final Submitted Version** | Окончательная версия **Application**, фактически поданная во внешний или внутренний процесс; должна сохраняться неизменяемо. |
| **Funding Decision** | Формальное решение о предоставлении или непредоставлении финансирования. |
| **Funding Opportunity / Call** | Возможность финансирования или объявленный конкурс либо программа приёма заявок. |
| **Handover / Handover Package** | Формализованная передача информации, документов и ответственности от одного подразделения или этапа следующему. |
| **Not Proceeded** | Состояние ещё не активированного **Project**, который был создан, но дальнейшая реализация по тому же **Award** была прекращена до полноценного запуска. |
| **Pending Closure** | Состояние **Project**, при котором закрытие уже применимо, но ещё не выполнены все блокирующие условия. |
| **Period Ended** | Вычисляемый факт завершения официального периода **Project**; не состояние жизненного цикла. |
| **Post-Award** | Административное сопровождение после получения права на реализацию проекта: подготовка **Project**, бюджет, изменения, обязательства, расходы, отчётность, мониторинг и закрытие. |
| **Post-Closure Obligation** | Обязательство, которое законно продолжается после административного закрытия **Project**. |
| **Pre-Award** | Работа до получения права на реализацию/финансирование проекта: возможности финансирования, заявки, административная проверка, сопровождение подачи и передача результата дальше. |
| **Pre-Award Application Check** | Проверка заявок, осуществляемая **Pre-Award**: административная и техническая проверка и поддержка заявки; не научная экспертиза. |
| **Project** | Самостоятельный объект администрирования исследования или договора после его создания в NURA ERP. |
| **Project Closure** | Административное закрытие **Project** после наступления условий закрытия и выполнения применимых **Closure-Blocking Condition / Obligation**. |
| **Project Setup** | Подготовительные административные действия после создания **Project**, необходимые для его нормального сопровождения. |
| **Project Type / Scenario** | Тип или сценарий **Project**, от которого могут зависеть правила, документы и **Authorizing Basis Requirement**. |
| **Proposal** | Предложение, подаваемое потенциальному грантодателю или заказчику; в отдельных сценариях этот термин может использоваться вместо **Application**. |
| **Research Administration** | Административное сопровождение научной деятельности: заявки, проекты, финансирование, договоры, закупки, отчётность, контроль обязательств и закрытие. |
| **Research Council Decision** | Решение Исследовательского совета; в отдельных сценариях может одновременно фиксировать **Funding Decision** и выступать как **Authorizing Instrument**. |
| **Setup Complete** | Результат проверки готовности **Project**; не состояние жизненного цикла. |

## 3. Термины Agreement / Contract и юридической работы

| Термин | Краткое пояснение |
|---|---|
| **Agreement Closeout** | Административное завершение **Agreement / Contract** после урегулирования применимых договорных обязательств и последствий. |
| **Agreement / Contract** | Юридически значимый договор или соглашение. В проекте конкретный термин сохраняется в зависимости от реального типа документа. |
| **Agreement / Contract Type** | Классификация юридического документа по его типу; сама по себе не определяет автоматически все его последствия. |
| **Amendment** | Формальное изменение к существующему **Agreement / Contract**; отдельная связанная **Business Entity**. |
| **Authorizing Basis Requirement** | Правило на уровне **Project**, определяющее, какие официальные документы, решения или их комбинации необходимы для бизнес-активации **Project**. |
| **Authorizing Instrument** | Конкретный официальный документ или решение, которое полностью или частично удовлетворяет **Authorizing Basis Requirement**. |
| **Composite Requirement** | Требование, которое может состоять из нескольких условий или документов, объединённых логикой «И», «ИЛИ» или условным правилом. |
| **Counterparty** | Внешняя сторона **Agreement / Contract**: грантодатель, заказчик, партнёр, поставщик и т. п. |
| **Counterparty Coordination** | Фактическое согласование документа с внешней стороной. Не обязательно является системным статусом жизненного цикла. |
| **Draft Preparation** | Подготовка черновика **Agreement / Contract** или **Amendment**. |
| **Early Termination / Early Cessation** | Досрочное прекращение действия **Agreement / Contract** или **Project** по определённому основанию. Рассматривается как причинное событие, а не просто конечный статус. |
| **EDMS Coordination / Approval / NURA Signature** | Формальный маршрут документа через **EDMS** для согласования, утверждения и, где применимо, подписи со стороны NURA. |
| **Effective** | Состояние, при котором документ вступил в силу по применимым юридическим условиям; не просто вручную установленный статус рабочего процесса. |
| **Effective Date / Effective From** | Дата, с которой документ или изменение юридически действует. |
| **Funding Agreement** | Договор или соглашение о финансировании **Project**. |
| **Internal Coordination** | Внутреннее содержательное согласование проекта документа внутри NURA или Университета. |
| **Legal Effect** | Юридическое действие документа: когда и при каких условиях он создаёт юридические последствия. |
| **Not Concluded** | Результат подготовки **Agreement / Contract**: работа начата, но договор окончательно не заключён. |
| **Pending Closeout** | Состояние, при котором **Agreement / Contract** ещё не может быть административно закрыт из-за незавершённых обязательств или последствий. |
| **Reason / Basis** | Причина либо юридическое или административное основание действия или решения. |
| **Research Contract** | Договор на выполнение исследовательских работ/услуг, не обязательно грантовой природы. |
| **Settlement** | Урегулирование финансовых или договорных последствий, например штрафов, возвратов и взаимных требований. |

## 4. Термины Funding и финансового учёта

| Термин | Краткое пояснение |
|---|---|
| **Accounting Actual** | Фактические данные бухгалтерского учёта, то есть бухгалтерский факт. Для NURA ERP авторитетным источником этих данных является 1C. |
| **Approved Allocation** | Сумма, утверждённо распределённая на конкретную **Budget Line / Category**. |
| **Available Budget** | Сумма, реально доступная для новых обязательств или расходов с учётом утверждённых распределений, **Commitment / Encumbrance** и фактических данных. |
| **Budget** | Утверждённая структура распределения средств и лимитов **Project**. |
| **Budget Line / Category** | Статья или категория **Budget**. |
| **Budget Version** | Неизменяемое утверждённое или историческое состояние **Budget** после управляемого изменения. |
| **Business Purpose** | Причина или назначение расхода либо действия; может быть связано с одним **Project**, даже если **Financial Attribution** относится к другому источнику. |
| **Commitment / Encumbrance** | Зарезервированное или уже возникшее финансовое обязательство, которое ещё может быть не оплачено. |
| **Direct-expense processes** | Процессы, связанные с прямыми расходами **Project**: например **Services**, **Travel**, **Publications** и другие расходы, которые не следует автоматически смешивать с **Goods Procurement**. |
| **Double Counting** | Двойной учёт: ошибка, при которой одна и та же сумма учитывается дважды при расчёте **Commitment / Encumbrance**, фактических данных или доступного остатка. |
| **Financial Attribution** | Указание, из какого **Funding Source** и **Budget** фактически финансируется расход. |
| **Funding** | Финансирование **Project**: разрешённые, ожидаемые или полученные источники и суммы; не то же самое, что **Budget**. |
| **Funding Mechanism** | Механизм финансирования: грант, совместное финансирование, договорное финансирование и другие применимые варианты. |
| **Funding Schedule** | План поступления финансирования по датам/этапам/траншам. |
| **Funding Source** | Конкретный источник средств, за счёт которого финансируется **Project** или расход. |
| **Operational Actual** | Оперативный финансовый факт, известный подразделению до окончательного отражения в бухгалтерской системе. |
| **Publications** | Расходы и административные действия, связанные с публикацией результатов исследования, включая применимые публикационные сборы. |
| **Reconciliation** | Сверка данных NURA ERP с авторитетным внешним фактом, например с данными 1C. |
| **Services** | Услуги для **Project**, приобретаемые или оформляемые отдельно от **Goods Procurement**, когда предметом является выполнение работ или оказание услуг. |
| **Travel** | Командировки и связанные с ними расходы в рамках **Project** или другой разрешённой деятельности. |
| **Unallocated Amount** | Часть общей разрешённой суммы, ещё не распределённая по статьям **Budget**; сама по себе не доступна для расходования. |

## 5. Термины Procurement

| Термин | Краткое пояснение |
|---|---|
| **Accepted Quantity** | Количество, фактически принятое NURA. |
| **Actual Receiver** | Человек, фактически принявший соответствующий товар или количество. |
| **Advance Delivery Notice** | Предварительное уведомление поставщика о предстоящей **Delivery**: какие товары, в каком количестве и когда будут доставлены по **Supplier Contract**. |
| **Announcement / Sourcing Round** | Объявление или раунд поиска предложений поставщиков внутри **Procurement Case**; не сам **Procurement Case**. |
| **Approved Procurement Plan Version** | Формально утверждённое неизменяемое состояние **Procurement Plan**, зафиксированное на определённую дату. |
| **Consolidated Approved Procurement Plan** | Сформированное консолидированное представление последнего формально утверждённого состояния **Procurement Plan**; не ежедневный рабочий план. |
| **Consolidation** | Объединение совместимых потребностей или позиций, в том числе из разных **Project**, для совместного проведения закупки. |
| **Consolidation Candidate** | Позиция или набор позиций, которые NURA ERP предлагает подразделению закупок рассмотреть для объединения; окончательное решение остаётся за **Procurement Office / Procurement**. |
| **Delivery** | Факт физической поставки товара или части товара; не равен **Goods Acceptance**. |
| **Delivery Item** | Конкретная позиция и количество в составе **Delivery**. |
| **Effective Procurement Plan** | Самое актуальное рабочее структурированное состояние **Procurement Plan** на текущий момент. |
| **Goods Acceptance** | Подтверждение фактического принятия товара по конкретным **Delivery Item** и количествам. |
| **Goods Procurement** | Закупка товаров или оборудования для **Project**. |
| **Lot** | Лот: группа закупочных позиций, по которой отдельно может определяться поставщик, победитель или результат. |
| **Procurement Case** | Рабочий контекст подразделения закупок для проведения и консолидации закупки; может объединять позиции из разных **Procurement Request** и **Project**. |
| **Procurement Item / Case Item** | Конкретная позиция товара и количества внутри **Procurement Request** или **Procurement Case**. |
| **Procurement Method** | Применимый способ закупки, определяющий правила и рабочий процесс выполнения **Procurement Case**. |
| **Procurement Plan** | План или реестр потребностей и закупочной работы; прежде всего инструмент планирования и мониторинга. |
| **Procurement Plan Amendment** | Официальный документ или пакет изменений к предыдущей **Approved Procurement Plan Version**. |
| **Procurement Procedure** | Не моделируется как отдельный **First-class Business Object**; процедурная логика задаётся через **Procurement Case**, **Procurement Method** и применимые бизнес-правила. |
| **Procurement Request** | Формальная заявка исследовательской команды на закупку конкретных товаров и количеств. |
| **Rejected Quantity** | Количество, которое не принято из-за несоответствия, повреждения или другой причины. |
| **Research Need** | Структурированная потребность **PI (Principal Investigator)** в товаре или оборудовании; объект планирования, а не весь жизненный цикл закупки. |
| **Split** | Разделение одной исходной потребности или позиции **Procurement Request** между несколькими **Procurement Case** либо последующими распределениями. |
| **Supplier Contract** | Договор с поставщиком, создающий внешнее закупочное обязательство. |

## 6. Термины объектов, процессов и жизненных циклов

| Термин | Краткое пояснение |
|---|---|
| **Business Change** | Реальное изменение бизнес-факта или условия. |
| **Business Entity** | Сущность предметной области; в этом проекте по смыслу обычно близка к **Business Object**, когда подчёркивается самостоятельность модели или идентичности. |
| **Business Fact** | Конкретный факт реального бизнеса, который система хранит сама или получает из авторитетного источника. |
| **Business Object** | Сущность предметной области с собственной бизнес-идентичностью, данными, связями, историей и, где применимо, собственным жизненным циклом. |
| **Controlled Exception Override** | Контролируемое разрешение на отклонение от конкретного правила, если для него явно допускается такое исключение. |
| **Data Correction** | Исправление ошибочно записанных данных без создания фиктивного бизнес-изменения. |
| **Derived Fact / Derived Status** | Факт или статус, который система вычисляет из более первичных данных, а не просит пользователя вводить вручную. |
| **Exception** | Исключительный сценарий, отклоняющийся от нормального маршрута. |
| **First-class Business Object** | Самостоятельный **Business Object** с собственной идентичностью, связями, историей и, где применимо, собственным жизненным циклом. |
| **Handoff** | Передача объекта или ответственности между ролями или подразделениями. |
| **Hard Business Validation** | Жёсткое бизнес-правило или проверка, которую нельзя обойти обычным **Controlled Exception Override**. |
| **Lifecycle** | Жизненный цикл объекта: допустимые бизнес-состояния и переходы самого объекта. |
| **Mandatory Setup Check** | Обязательная проверка готовности **Project** до предоставления **Operational Authorization**. |
| **Operational Authorization** | Явное управленческое разрешение на определённые операционные действия, например инициирование расходов. |
| **Operational Restriction** | Динамическое ограничение на отдельные действия **Project**; не то же самое, что состояние жизненного цикла. |
| **Outcome** | Бизнес-результат процесса или решения. |
| **Override** | Разрешённое уполномоченным лицом отступление от правила или ограничения, для которого допускается контролируемое исключение. |
| **Process** | Более широкая бизнес-последовательность от события или условия запуска до результата; может включать несколько **Workflow** и **Business Object**. |
| **Process Design** | Проектирование того, как должен работать бизнес-процесс: роли, шаги, правила, исключения, передачи ответственности и результаты. |
| **Project-centered, but not Project-only** | Архитектурный принцип: **Project** является центральным контекстом, но самостоятельные **Business Object** не должны искусственно сливаться с ним. |
| **Reconciliation Exception** | Зафиксированное расхождение между операционными данными NURA ERP и авторитетным внешним фактом. |
| **State / Status** | Состояние объекта. Не каждое действие процесса должно становиться состоянием объекта. |
| **Trigger** | Событие или условие, запускающее процесс или действие. |
| **Workflow** | Управляемая последовательность действий, назначений, решений и ожиданий. |

## 7. Термины данных, документов и авторитетности источников

| Термин | Краткое пояснение |
|---|---|
| **Audit Trail** | Прослеживаемая история значимых действий и изменений: кто, что, когда и на каком основании сделал. |
| **Authoritative Source** | Источник, которому принадлежит право определять конкретный факт в своей области полномочий. |
| **Cardinality** | Допустимое количество связей между объектами: один к одному, один ко многим, многие ко многим и т. п. |
| **Data Domain** | Логическая область данных с собственными объектами, правилами и ответственностью. |
| **Derived View** | Вычисляемое или сформированное представление данных, которое строится из первичных фактов и не является отдельным авторитетным источником истины. |
| **Document** | Содержательный документ, например договор, отчёт, решение или сформированная системой форма. Не равен **File**. |
| **File** | Конкретный цифровой файл определённого формата. Один **Document** может иметь несколько файлов и версий. |
| **Master Data** | Ключевые относительно устойчивые данные о базовых объектах, используемые многими процессами. |
| **Provenance** | Происхождение данных: откуда они пришли, каким источником, документом или процессом подтверждаются. |
| **Reference Data** | Управляемые справочные значения, например типы, категории, статусы и классификаторы. |
| **Snapshot** | Зафиксированное состояние данных на определённый момент; обычно сохраняется неизменяемо для истории или формального утверждения. |
| **Structured Data** | Данные, хранимые в формализованном виде по полям, сущностям и связям и пригодные для поиска, применения правил, расчётов и отчётности. |
| **System of Record (SoR)** | Авторитетная система-источник для конкретного типа данных или факта. Это не означает, что одна система является авторитетной для всех данных организации. |
| **Template / Template Version** | Управляемый шаблон документа и конкретная его версия. |
| **Temporal Constraint** | Ограничение связи или факта во времени: когда он действует, может пересекаться с другими периодами, прекращается и т. п. |
| **Version** | Отдельное историческое или утверждённое состояние объекта или документа. |

## 8. Архитектурные и технические термины

| Термин | Краткое пояснение |
|---|---|
| **API** | Программный интерфейс для автоматизированного взаимодействия систем. Наличие **API** нельзя предполагать без проверки. |
| **Application Architecture** | Структура программного приложения: модули, границы, взаимодействия и ответственность компонентов. |
| **Availability** | Доступность системы для использования в требуемое время. |
| **Backup / Recovery** | Резервное копирование и восстановление системы или данных после сбоя. |
| **Business Analysis** | Анализ бизнес-контекста, требований, правил, ролей, проблем и терминологии. |
| **Capacity Sizing** | Оценка требуемых вычислительных ресурсов, оперативной памяти, хранилища и сети с учётом нагрузки и роста. |
| **CI/CD** | Автоматизированные процессы сборки, тестирования и развёртывания изменений приложения. |
| **Data Architecture** | Организация областей данных (**Data Domain**), владения данными, авторитетных систем-источников (**System of Record (SoR)**), жизненного цикла, управления данными и потоков данных. |
| **Data Model** | Концептуальная или логическая модель сущностей, атрибутов и связей. |
| **Database Engine** | Конкретная система управления базами данных или её программный движок. |
| **Degraded Mode** | Работа системы в ограниченном режиме при недоступности внешней зависимости или части функций. |
| **Deployment** | Развёртывание приложения и инфраструктуры в конкретной среде. |
| **DevOps** | Практики, связывающие разработку и эксплуатацию: поставку изменений, управление средами, автоматизацию, мониторинг и поддерживаемость. |
| **EDMS** | Система электронного документооборота, используемая для официального согласования, регистрации и, где применимо, подписания документов. |
| **Enterprise Architecture** | Более широкий архитектурный уровень: место решения в организации, карта возможностей, ландшафт приложений и целевая архитектура. |
| **ERP** | Информационная система класса управления ресурсами и операционными процессами организации; в этом проекте — NURA ERP. |
| **IAM** | Управление идентичностью пользователей и доступом: учётными записями, ролями, правами и связанными правилами. |
| **Information Architecture** | Организация информации для пользователей: таксономия, метаданные, классификация документов, правила именования, поиск и навигация. |
| **Integration** | Обмен данными и взаимодействие между NURA ERP и другими системами. |
| **Interface** | Точка или механизм взаимодействия систем или компонентов; может быть **API**, файл, очередь сообщений, пользовательский интерфейс и т. п. |
| **Layered Architecture** | Разделение архитектуры по уровням ответственности. В NURA ERP означает, в частности, что бизнес-, процессная и системная семантика не смешиваются с технической реализацией. |
| **Least Privilege** | Принцип предоставления пользователю или компоненту только минимально необходимых прав доступа. |
| **Low-Code Platform** | Платформа, позволяющая конфигурировать бизнес-логику с минимальным программированием. В NURA ERP универсальная неограниченная такая платформа или **Rules Engine** не считается автоматически предпочтительным решением. |
| **Maintainability** | Удобство сопровождения, исправления и развития системы. |
| **Non-Functional Requirement (NFR)** | Требование не к отдельной бизнес-функции, а к качественным характеристикам системы: производительности, доступности, безопасности, восстанавливаемости и т. п. |
| **Object Storage** | Хранилище файлов и других бинарных объектов, рассчитанное на работу с большим количеством таких объектов. |
| **Observability** | Способность понимать состояние системы по журналам, метрикам, трассировке и другим диагностическим данным. |
| **Performance** | Скорость и производительность системы при реальной нагрузке. |
| **Process Architecture** | Архитектура сквозных бизнес-процессов, их границ, передач ответственности (**Handoff**), ролей и результатов (**Outcome**). |
| **Production** | Рабочая эксплуатационная среда с реальными пользователями и данными. |
| **Role-Based / Context-Based Access** | Доступ определяется не только общей ролью пользователя, но и его отношением к конкретному **Project** или **Business Object**. |
| **RPO** | Допустимый объём потери данных при восстановлении после сбоя, выраженный во времени. |
| **RTO** | Допустимое время восстановления сервиса после сбоя. |
| **Rules Engine** | Компонент для выполнения конфигурируемых бизнес-правил. В NURA ERP требуется контролируемая и ограниченная применимость, а не универсальная среда программирования. |
| **S3-compatible Storage** | Объектное хранилище, поддерживающее программный интерфейс, совместимый со стандартом S3; само по себе не означает размещение в публичном облаке. |
| **Separation of Duties (SoD)** | Разделение несовместимых полномочий между ролями, чтобы один пользователь не мог бесконтрольно выполнить конфликтующие действия. |
| **Solution Architecture** | Техническая архитектура конкретного решения: структура приложения, интеграции, хранение данных, безопасность, технологический стек, развёртывание и эксплуатация. |
| **System Analysis** | Перевод бизнес- и процессной семантики в требования к поведению информационной системы. |
| **Technology Stack / Programming Stack** | Набор языков программирования, программных каркасов, сред выполнения и других технологий реализации. |
| **Testing / Training Environment** | Отдельная среда для тестирования или обучения, не являющаяся **Production**. |
| **Vendor Replaceability** | Возможность сменить подрядчика или команду без критической зависимости от одного поставщика знаний или технологий. |

## 11. Правило ведения справочника

При каждом следующем rewrite Part 01–08 ARCHITECT должен:

1. проверять новые существенные английские термины;
2. добавлять термин в справочник, если без пояснения он может быть неоднозначен для бизнес-пользователя или нетехнического читателя;
3. располагать термины внутри каждого тематического раздела по алфавиту;
4. не создавать дубликаты с разными переводами;
5. при изменении архитектурной семантики обновлять определение существующего термина;
6. в пояснениях использовать русский язык; английский оставлять только для терминов, которые сами расшифрованы в справочнике, и для собственных наименований систем, организаций, технологий и форматов;
7. сохранять различие между официальным именем Business Object или State и русским пояснением его смысла.
